# HolterSQA replay protocol

A client opens a TCP connection and sends a `hello` frame containing its session identifier, record identifier, ECG and accelerometer headers, and requested packet duration. The server acknowledges it with `hello_ack` and the effective duration and model window. A record identifier can refer to another recording from a person already represented by a different record.

Each frame uses the four-byte magic `EKG2`, protocol version 1, a UTF-8 JSON header and an optional binary payload. The network-order prefix is `!4sBIQI` (magic, version, header length, payload length and CRC32). A `data` header describes the named ECG and acceleration blocks, their dimensions, sample frequencies, units and offsets. The accompanying binary arrays use the dtype declared in each descriptor. The CRC32 covers header and payload. The source checks the declared bounds and rejects malformed frames.

Clients number packets and retain pending frames until acknowledged. On reconnect the peers exchange resume and next-sequence information. Control frames support interval negotiation, connection feedback and a generic alert. The default requested packet interval is 2 s. A complete 10 s model window is needed before the first saved-MLP prediction. Each subsequently processed data packet triggers evaluation of the latest complete window. With 2 s packets the nominal step is 2 s. The ML pipeline applies zero-phase filtering to that already-received window. Display filtering has a separate state.

The tested functional example binds to 127.0.0.1. The GUI has a configurable bind address and can listen on all interfaces. Enter 127.0.0.1 for a local demonstration. The present transport has no application-level authentication or encryption. The client sends record metadata in its handshake. Use the public research recordings on loopback for the documented example. The example measures receipt of a model prediction. Packet duration and model-window duration describe data handling, not a measured end-to-end delay.
